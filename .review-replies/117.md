Thanks Nic — all addressed in a151ea7 (plus the stack re-based on it). Point by point:

**Links only created in the same run / "retried on --update" (whole stack).** True as written. Fixed for Jira in a151ea7: `Publish` now reconciles parent (Cloud `parent` / DC Epic Link) and `blocks` links against what the issues actually carry on every run, including no-op runs and existing children, so a failed link, a new `depends_on` or a re-created Epic is repaired. Linear gets the same in #118 (0cf22c8). The GitHub target on `main` has the same gap; I've removed the "retried on --update" claim from this description and github.go's comment comes out with the fix, which I'll send as a separate PR against `main` as you suggested.

**DC Stories under an Epic.** Fixed. With `epic_link_field` unset on DC, the target discovers the Epic Link field from `GET /rest/api/2/field` (`schema.custom == com.pyxis.greenhopper.jira:gp-epic-link`) and refuses with a `next_action` naming `epic_link_field` if none is found; `parent` is only ever sent for sub-tasks on DC. The DC fake now serves `/rest/api/2/field` and returns 400 `errors.parent` for `parent` on any non-"Sub-task" type — the old code fails against it; the e2e in #119 asserts the Epic Link field (not `parent`) is what a DC Story carries.

**Find on Cloud / unescaped Lucene.** Fixed. `Find` no longer uses property JQL at all; it searches `project = X AND description ~ "<token>"` where the token is `spekpub` + 16 hex of sha256("spek:publish " + artifact_id) — a single alphanumeric word, nothing to escape. The token is written into the description on the line before the marker. The fakes have no property-search path any more.

**Create, then set the property.** Fixed. The property goes in the `properties` array of `POST /rest/api/2/issue` (and on `PUT`), so there is no window where an issue exists without it. The fake asserts it on create.

**Re-run after a partial failure / eventual consistency.** Fixed two ways: (1) `published:` is now written after a partial failure with whatever was filed so far (`filedSoFar`), and (2) the target gets a `Hint(urls)` of recorded URLs and reads those issues directly by key (`GET issue/KEY`, 404 skipped) before searching, so a re-run is independent of the search index. The Jira fake has a `SearchLag` mode (nothing searchable until `Reindex()`) and the #119 e2e runs with it on throughout; `FailCreateAfter(n)` covers the partial-failure case in `cmd/publish_test.go`.

**Minor: marker visible in the description.** Left as is, deliberately: hive's `spekmarker` package reads the marker from issue bodies (it's what drives the never-claim-the-RFC and clarity-gate behaviour), and Jira exposes neither property values nor a hidden node to a body reader — ADF has no comment node and `{expand}`/panel content is still visible text. So the marker has to be in the body. It's confined to one trailing line after the `---` footer, and the property additionally carries it for anything that reads properties. If hive grows a property reader we can drop the body copy then.
