## 000059_normalise-artifact-addressing

One name now reaches every document a feature produces. A spec and a changelog record are addressed by the feature's bare name, exactly the name the workflow records in `data.name`, and a plan document by that name plus a document name (`plan`, `context`, `research`, `test-plan`). Every `name` a list command prints is accepted unchanged by read, write, delete and set-document-status, so an agent or an external orchestrator never has to join segments or append an extension. A name that carries an extension, or a plan written as one joined path, is refused with `unexpected_extension`, and reading a plan with no document name is refused with `document_required` instead of an internal error that leaked a host path; both refusals give the correct command as their next action. Reported locations are now portable: a list's `path`, the `plan_path` from `plan status` and `implement status`, and the `spec_path`/`plan_path` in workflow results are relative to the folder holding the configuration file that declares the store, and step instructions name documents and the command that reads them rather than pointing at host files.

**Breaking change**: spec, plan and changelog document commands no longer accept file extensions or joined plan paths. `spec file read <name>.md` is now `spec file read <name>`; `plan file read <name>/plan.md` is now `plan file read <name> plan` (likewise `write`, `delete`, `set-document-status`); `changelog file read <name>.md` is now `changelog file read <name>`. `plan file list <name>` names documents `plan`, `context` and so on rather than `plan.md`, and `spec file list` and `changelog file list` no longer take a sub-path. The old spellings are refused with `unexpected_extension`, whose `next_action` shows the new command. List `path` values and the `plan_path` reported by `plan status` and `implement status` are now relative to the folder holding the declaring config file (for example `specs/<name>.md` rather than `.spektacular/specs/<name>.md` or an absolute path), and both status commands add `plan_document`. Nothing on disk moves; installed skills pick up the new spellings through `spektacular migrate` or `init`.

## 000050_knowledge-location-resolution

Relative locations in a project's `config.yaml` now all resolve from the same place: the folder holding `config.yaml`. Previously a repos entry resolved from there while a `knowledge.sources` entry resolved from the project root one level up, so two paths written three lines apart in the same file needed a different number of `../` segments to reach the same directory. Nothing warned about the difference, and a knowledge location written under the repos convention either failed as unreachable or, if it happened to land on a real directory, quietly loaded the wrong store.

**Breaking change**: a project whose `knowledge.sources` entry uses a relative location must add one `../` segment, so `../team-kb` becomes `../../team-kb`. Absolute locations are unaffected, as are each repo's own knowledge sources, which resolve from that repo's root and always did. The change is not applied automatically, but it reports itself: a store that no longer resolves fails fast naming the store, the path it resolved to, and the base it resolved from, and when the store is found where the previous rule would have put it the error names the exact replacement value to write into `config.yaml`.

## 000047_repo-scoped-knowledge-addressing

Knowledge is now addressed explicitly, so a project that brings several repositories together can say which knowledge it means. Every request states a tier — the project's shared knowledge, the repositories' own, or both — and names one store within it. Writing an entry says where it belongs and lands there; a write that leaves either the tier or the store name unstated is refused and told which stores are available, instead of quietly landing in whichever store happened to sort first. Every listing entry, search hit, and read result reports the tier and store it came from, so a hit carries exactly what a read needs and can be fetched back without a second lookup even when a same-named entry exists elsewhere. Searching, listing, conventions, and the always-applied load take `--tier` and a repeatable `--filter`, replacing the narrower `--repo` option, and the narrowing is honoured with no exceptions: a store that is not named is not included, and no store is included merely because it was hard to attribute. Planning scoped to one repository therefore stops loading every other repository's standing rules.

**Breaking change**: knowledge is now addressed by tier and store name. A repo declares its single knowledge store as one provider block in `repo.yaml`, and the project names each of its shared stores under `knowledge.sources`. Configuration in the previous form is rejected with an error naming the file and the required shape; it is not migrated automatically. Existing projects make two one-time edits: replace each repo's `knowledge.sources` list with a single `provider`/`config` block, and rename each project-declared source's `scope:` key to `name:`.

## 000045_config-file-migration

Spektacular now automatically detects and prompts for migration when upgrading from the legacy single-file config.yaml format to the new split configuration (config.yaml + repo.yaml) introduced for multi-repo project support. When you run `spektacular version check` in a project with only config.yaml, the command returns a migration prompt explaining that a backup will be created (config.yaml.old) and repo.yaml will be generated with metadata scanned from your project files (README.md, go.mod, package.json, Makefile, Dockerfile). The migration ensures existing Spektacular users can upgrade smoothly without manual configuration changes or errors.

## 000044_projects-feature-documentation

Spektacular's multi-repo "projects" capability, registering more than one repository, splitting configuration between project membership and each repository's own description, attributing planning and implementation work across repos, and excluding paths from search, is now documented on the documentation site with a new reference page reachable from the site's navigation. The getting-started tutorial now points to it at the moment a reader might otherwise assume a project is limited to one repository, and this README's configuration section has been corrected where its example had drifted out of date and now links to the fuller explanation as well.

## 000043_flipped-interaction-spec-interview

Creating a spec now opens with an adaptive interview instead of a fixed sequence of scripted questions: the agent asks open questions about what you're building, following up on what you've already said rather than working through a script, and stops once it has enough to draft a credible first pass. In a project with more than one registered repo, the interview also knows the full roster and asks whether a feature that reads as focused on one repo needs changes in the others. Every section of the spec is then drafted from the interview and presented to you for confirmation rather than asked from a blank prompt, and if you reject a draft, the agent asks why before changing anything — a single correction can turn out to need more than one change, including to a different, already-confirmed section, without requiring you to separately revisit and re-approve it in the moment. The existing end-of-workflow review remains the one place everything, including any such correction, gets checked together.

## 000042_repo-self-describing-metadata

A registered repository's description, role, tags, and deployment now live in the repository's own configuration file instead of being copied into every project that registers it, so a shared repository describes itself consistently everywhere it's used. Registering a repository with this metadata writes it directly into that repository's own config, and editing it there is picked up immediately by every project that lists or plans with that repository, with no per-project re-entry needed. A project's own registry now records only what's needed to find and identify a member repository — its name, location, provider, and dependencies on other registered repositories.

## 000039_project-level-capabilities

Spektacular is now project-aware: one project can register several repositories — a code repo plus a docs repo, say — and plan, implement, and record work across all of them as a single unit, with planning attributing each requirement to the repo it belongs to and every touched repo receiving its own provenance-stamped changelog entry that names the project and spec that produced it. Repos registered by remote address are cloned automatically on first use (never fetched or pulled behind your back), and a gitignore-style `.spektacular_ignore` file keeps noise like build artifacts out of Spektacular's searches without ever blocking direct access to a named file. **Breaking change**: configuration is now split into a project-level file (with a required project name and the repo registry) and a per-repo file, and running Spektacular outside an initialized project fails with a clear error instead of silently using defaults — existing setups re-initialize once with `spektacular init <agent>`.

## 000041_workflow-knowledge-capture-offers

The implement and plan workflows now recognize the two moments when durable project knowledge most often surfaces and offer — right then, in the same conversation — to save it to the project's knowledge base. When an implement run records what a completed phase discovered, it weighs each discovery for durability (an undocumented coupling, a surprising contract, a convention nobody wrote down) and offers to capture anything that matters beyond the current change; when you correct a drafted plan during its review, the workflow considers what the correction reveals — a wrong drafting default, a constraint only you knew — and offers to capture the general lesson. Offers are deliberately rare: change-local discoveries and cosmetic corrections produce none, nothing is ever written without your explicit acceptance, and a declined offer is not raised again for the rest of the conversation. Insights that used to end up buried in per-change history now get captured once, when they appear, so future plans and implementations stop re-discovering them.

## 000040_plan-draft-then-walkthrough

Creating a plan no longer interrupts you with roughly ten section-by-section approval prompts. The workflow now drafts the entire plan autonomously — making reasonable judgement calls itself, including the choice of design direction, and recording each one durably with its rationale and the alternatives it rejected — stopping only for a genuinely blocking question that has no reasonable default. When the draft is complete, a new mandatory walkthrough reviews it with you like a colleague would: the plan is presented in natural beats, every recorded assumption is raised for challenge, any change you request is applied to the saved documents immediately, and the plan is only marked approved once you give an explicit yes to a direct closing question — silence or ambiguity keeps the review open, an interrupted review resumes in a later session, and implementation cannot start against a plan whose review never closed. The final plan documents keep their exact shape and location, so downstream implementation is unaffected.

## 000038_artifact_metadata

Every workflow-produced document — specifications, plan documents, per-change changelog entries, and test plans — now carries a small YAML frontmatter block recording when it was created, what its lifecycle status is (in-progress, completed, superseded, or archived), and the date it entered a closed state. Workflows attach and update this metadata automatically as they own the documents through their lifecycle, so the age and status of any artifact you open is now visible at the top of the file rather than something you have to infer from git history. Two new query surfaces let you find artifacts by their metadata without opening files: every `spec/plan/changelog file list` command gained `--status`, `--created-after`, `--created-before`, `--closed-after`, `--closed-before` flags combinable in one query, and a new top-level `spektacular artifacts list` command returns matches across every artifact class at once, tagged with a `kind` discriminant. Existing pre-shipping documents stay untouched — they surface in unfiltered listings but naturally drop out of any query that sets a metadata filter.

## 000037_spec_plan_historical_artifacts

Agents working in a Spektacular-initialized repository now automatically treat every spec and every plan as a historical, archaeological record — a snapshot of *why* a past change was proposed and what its author intended, not a description of what the codebase does today. When you ask an agent to explore the codebase or explain how something currently works, it grounds its answer in source code, tests, and configuration rather than reading from the specs and plans stores, so its answers stay aligned with the shipped code even when the original intent shifted during implementation or was abandoned. When you ask a genuinely historical question — "why was X built this way?", "what was the original plan for Y?" — the agent still reaches for the relevant spec or plan and cites it as historical context; and while a spec, plan, or implement workflow is actively running, the workflow keeps full read/write access to its own live artifact. You should no longer need to remind agents mid-session that specs and plans aren't current-state documentation.

## 000036_present-drafts-as-text-not-dialog

The assistant now always shows you a drafted piece of content — an architecture write-up, a set of options, a written section, a summary — as plain, readable chat text before asking you to confirm it, instead of sometimes embedding the draft itself inside a compressed yes/no or multiple-choice dialog. Once the draft has been shown in full, a short confirmation question may follow, but only as a separate step afterward, never as a substitute for showing the draft itself. This applies consistently across every workflow — spec, plan, and implement alike — for every Spektacular-managed project, regardless of which coding agent you're using (Claude, Codex, or Bob).

## 000035_plan-walkthrough-conversation

After Spektacular finishes generating an implementation plan, the assistant now offers to walk you through it conversationally instead of just handing you the documents. If you accept, it explains the plan the way a colleague would — the reasoning behind the chosen approach, how the work breaks into stages, and what was deliberately left out — as a short back-and-forth rather than reading the plan aloud. You can interrupt at any point with a question or a change request; any change you ask for is applied to the plan immediately and confirmed before the conversation continues, and the walkthrough only wraps up once you explicitly say the plan looks right. Reading the documents yourself remains just as valid as before — the offer is made once, and declining it changes nothing about how the workflow finishes.

## 000034_spec-plan-implement-reconciliation

Spektacular now checks a plan against its own specification before implementation starts, and reconciles the specification's checklist against the finished work when it's done. Before any code gets written, the assistant compares the plan against the specification's Requirements and Acceptance Criteria; if something the spec asked for isn't covered by the plan, you're shown exactly what's missing and asked to either update the plan or explicitly accept the gap — and once you accept a gap, you won't be asked about it again on a later run. When implementation finishes, the specification's own checkboxes are updated to reflect what was actually built, and the final summary now tells you plainly which requirements are satisfied and, for anything left open, why — so you no longer have to open the specification yourself to find out.

## 000032_spec-workflow-pair-programming-enhancements

Coding agents working in a Spektacular-initialized project can now recognize when an open-ended discussion has become substantial enough to warrant a specification, and proactively offer to capture it instead of waiting to be asked. How readily they offer is configurable per-project (a new `spec_trigger_threshold` setting, defaulting to a balanced middle ground), and a change to that setting takes effect immediately without needing to re-run setup. If you accept the offer, the agent starts the spec workflow and drafts answers from the conversation you already had — proposing them for your confirmation rather than asking the same questions again from scratch. Saying "not yet" keeps the conversation open and the offer may come up again later; declining drops it for the rest of that discussion. Separately, when you start a spec workflow, Spektacular also captures the conversation context that led to it: the spec's `new` step clears `.spektacular/context.md` and instructs the agent to write detailed discussion context — the problem identified, requirements and constraints discussed, alternatives considered, and the user's exact phrasing for key requirements — so that context persists for resumption if the workflow is interrupted. If no meaningful context exists, the agent skips the write, keeping the file empty.

## spec-workflow-output-changelog

Every feature Spektacular finishes building now gets its own durable, self-contained changelog record automatically — no extra step required. When an implementation wraps up, the assistant writes a plain-language summary of what was actually built, why it matters, and where it diverged from the original plan, and stores it under a name you can retrieve later without hunting through the original spec, plan, or conversation. The workflow's final summary now tells you exactly where that record lives, alongside the other artifacts it already reports.

## 000031_agent-session-debug-log

Spektacular can now keep a local, opt-in record of everything an agent does during a session, so a different agent (or a person) can later reconstruct what happened without needing the original agent's memory of it. Turn it on with the existing `debug.enabled` setting in a project's config file — no new flag or environment variable — and every command issued and every response received, including rejected and failed commands, gets appended to a plain local file that's never committed to version control. Each entry also states whether the command actually moved the work forward, catching cases like re-running a step that's already current, which look successful but silently made no progress; and entries are automatically grouped by the piece of work they belong to, so unrelated sessions in the same project never get tangled together. Turning this on has no effect on the tool's normal behavior or output — it stays off by default.

## 000030_agent-actionable-errors

Every command now reports success or failure through one reliable channel: a single JSON response on the same output stream, always carrying a clear signal of which it is, with the process's exit code always agreeing. Failures now say exactly what went wrong and what to do about it — a rejected step request names your current position and the steps that would actually succeed next, a missing file or entry is named specifically rather than reported as a generic "not found," and an in-progress or wrong-kind workflow is reported the same way any other failure is, with concrete commands to resume or start over. A workflow that fails partway through a step can no longer report more progress than actually happened, so a later status check or resume always reflects reality. Nothing is ever printed twice.

## 000029_readme-refresh

The project README has been refreshed into an accurate, concise front door that matches what Spektacular actually does today. Claims for things that never shipped — a terminal UI, complexity scoring, and routing work to different models by complexity — are gone, the supported coding agents are now stated correctly as claude, bob, and codex (no more Aider or Cursor), and every repository link and the install instructions point at the real project and the Go binary rather than a stale path and a pinned version. The capability sections were rewritten to current behaviour: how the spec → plan → implement workflow works, what initialising a project sets up for each agent, the knowledge base's six categories and two retrieval tiers, configuration, testing, and building — each linking out to the documentation site for full detail. No tool behaviour or documentation-site content changed; only the README was updated.

## 000028_knowledge-base-categories-tiers-and-dedup

The knowledge base is now organised into well-defined categories — conventions, glossary, architecture, gotchas, learnings, and decisions — each with a real, self-explanatory definition instead of a placeholder, so contributors and the assistant know exactly what belongs where; new entries are routed to the right category as they are filed, with over-long content steered out of the glossary. Knowledge now has two retrieval tiers stated in one place: the rules and shared vocabulary a team always wants (conventions and glossary) are loaded in full on every task, while the larger reference body is looked up only when a query matches — and every search result is now labelled with the kind of knowledge it is. Asking the knowledge base a question returns a single consolidated, source-cited answer: byte-identical copies held in more than one place are removed automatically, differently-worded equivalents are merged, the most specific source wins when they overlap, and genuine disagreements are surfaced rather than silently dropped. Freshly initialised projects gain the new glossary and decisions categories automatically, and the whole model is written up in `docs/knowledge-base.md`; the existing `knowledge conventions` command and search output remain backward-compatible.

## 000027_document-level-search

Knowledge search now answers at the level searchers act on — the document. A multi-word query matches an entry when every word appears somewhere in it, in any order and at any distance, so queries like "workflow steps" find the entry whose words never share a line instead of returning nothing. Each matching entry comes back exactly once — no more dozens of repetitive line hits for a broad query — ranked strongest match first, and every result now carries the entry's title (its first heading, or its locator when it has none), a score summing every query word's occurrences across the document, and up to three excerpts showing its strongest matching lines. Single-word searches find exactly the entries they found before, matching stays literal and case-insensitive, conventions and binary files stay out of the results, and reading a chosen entry is unchanged: pass a result's scope and path to `knowledge read` exactly as before. The JSON output shape changed with this release — each hit's singular `excerpt` field is replaced by an `excerpts` array and gains `title`, and `score` now counts occurrences across the whole document — so any external consumer of `knowledge search` output must adapt; everything Spektacular ships (command schema and help, the knowledge skill, planning instructions, README) moves in lockstep.

## 000026_ripgrep-replace

Knowledge search is now fully built in: Spektacular no longer looks for, runs, or depends on the ripgrep tool, so a fresh install on a clean machine searches successfully with nothing else installed, and results are identical on every machine. Search got strictly better along the way — every hit now carries a relevance score (how many times the query appears in the matching line), binary files are quietly skipped instead of surfacing garbage excerpts, and a file containing a pathologically long line no longer aborts the whole search, only the rest of that file. Users who had ripgrep installed lose nothing; it simply stops being consulted. Searching by keyword, the excluded conventions area, and the output format are all unchanged.

## 000025_convention-aware-planning

Creating a plan now actively draws on the project's accumulated know-how. Conventions — the always-apply standards a project commits to — move from a single flat file into a dedicated `conventions/` area where each rule lives in its own file, so they can be added or changed independently. When you plan a feature, the discovery step reads every convention in full and then searches the rest of the knowledge base only for the specific surfaces the work touches, rather than one broad sweep that gets noisier as the knowledge base grows. The conventions that actually bear on the work — and only those — are written into the finished plan in a dedicated Conventions section, each with a one-line reason it applies; when nothing is relevant (or a project has none), the section says so plainly, which doubles as a visible signal that the knowledge base was consulted. Whoever implements the plan follows a document that already states which standards apply, without consulting the knowledge base themselves. A new `spektacular knowledge conventions` command returns every convention's full text, and topic searches no longer surface conventions twice. New projects get the `conventions/` layout automatically on `spektacular init`.

## 000024_resume

An interrupted spec, plan, or implement workflow can now be resumed instead of lost. Previously, re-running `spec new`, `plan new`, or `implement new` wiped any half-finished workflow before starting over, so a session ended by a crash, reboot, or closed terminal had to restart from scratch. Now re-running one of those commands detects an in-progress workflow and reports it — its kind, name, and the step it stopped on — without touching anything on disk, and the driving agent offers to resume from exactly where it left off or start over. Resuming re-presents the interrupted step with the prior session's completed work intact and rehydrates its accumulated working context from a git-tracked `.spektacular/context.md` file, so even a brand-new session after a reboot picks the effort back up. Pass `--force` to deliberately discard an in-progress workflow and start fresh (the old state stays recoverable through git).

## 000023_context-over-memory

Spektacular now redirects what coding agents would normally save into their own per-user, per-machine memory store into the project's shared knowledge base instead. When you work in a Spektacular-initialised repo with Claude, Codex, or Bob and the agent identifies a convention, gotcha, project fact, or preference worth remembering, it proposes a write to the project knowledge store via the `spek-knowledge` skill — you review the entry, choose the scope, and confirm before anything is persisted — so the captured knowledge ends up in git and travels with the project for every collaborator. Outside this repo, the same agents keep using their per-user memory as normal. The redirect is installed as a managed "Memory & Context" section in `AGENTS.md` by `spektacular init`; re-running init for the same agent or a different one updates that section in place without duplicating, and it sits alongside (not inside) any existing `tessl install` block. Existing projects pick this up by re-running `spektacular init <agent>` once.

## 000022_spek-knowledge-skill

Spektacular now ships a fourth workflow skill — `spek-knowledge` — that lets you read, contribute to, and update the project's knowledge base in any session without starting a formal spec or plan flow. Ask in natural language ("what do we know about X?", "remember Y", "update what we have on Z") and the agent runs the matching `spektacular knowledge` command, shows search results with their source scope labelled, and — for any write — presents the proposed scope, path, and body and waits for your explicit confirmation before persisting. The skill installs alongside `spek-new`, `spek-plan`, and `spek-implement` for every supported agent (claude, codex, bob); existing projects pick it up by re-running `spektacular init <agent>`.

## 000021_file-writing

Writing a spec or plan file through Spektacular no longer goes through standard input. `spektacular spec file write` and `spektacular plan file write` now take a required `--from <path>` flag pointing at a source file on disk, and the contents arrive in the store byte-for-byte — backticks, dollar signs, quotes, and newlines all survive intact, where the previous shell-piped form would mangle them. Pointing `--from` at a missing path fails cleanly with the offending path in the error message, and the source file is left untouched after a successful write. The workflow skill and step prompts shipped with Spektacular have been updated to drive the new form (stage under `.spektacular/tmp/`, write with `--from`, `rm` the scratch file), and a regression test guards the instruction surface so the old stdin form cannot creep back in. The stdin path has been removed outright with no compatibility shim, so any external script that piped content into `file write` must switch to `--from <path>`.

## 000020_context

Spektacular now draws on a multi-source knowledge layer when planning. Instead of one fixed knowledge folder, a project can configure several knowledge sources at distinct scopes — `project`, `team`, `global`, and so on — each independently located and keyword-searchable, so teams can share architectural notes, conventions, and past learnings while keeping private ones private. A new `spektacular knowledge` command lets agents search every source with one query (results tagged by where they came from), read a full entry, list everything available, write a new entry into a chosen scope, and inspect the configured sources; an unreachable source fails loudly rather than silently returning a partial answer. Configuration is now provider-based: `spec`, `plan`, and `knowledge` each name a provider and a config block, which also makes the spec and plan output directories configurable for the first time. Projects with no `knowledge` configuration keep working unchanged via a synthesised default source. The `config.yaml` format has changed — `spec`, `plan`, and `knowledge` each gain a `provider` field and a provider-specific `config` block; `spec.id_method` stays a sibling of `provider` since identifier generation is independent of the storage backend. Update existing config files to the new shape, or remove the stale section to fall back to defaults.

## spec-id-prefix-method

Spec creation now uses CLI-owned identifier prefixes. By default, `spec new` creates timestamp-prefixed spec names, accepts an optional `id` for external systems, and can be configured with `spec.id_method: timestamp`, `counter`, or `external`. Callers should use the returned `spec_name` and `spec_path` because requested names and ids are normalized before workflow state and files are created.

## 19_codex_integration

Spektacular now ships first-class support for OpenAI Codex alongside Claude Code and Bob. `spektacular init codex` installs the three workflow entry points — spec, plan, and implement — as native SKILL.md files, so Codex users can invoke `$spek-new`, `$spek-plan`, and `$spek-implement` out of the box. As part of this release the workflow entry points become the canonical artefact type across every supported agent: slash commands for Claude and Bob are now thin wrappers that simply invoke the matching skill, and workflow instructions live in one place rather than being copied per-agent. Existing Claude and Bob users should re-run `spektacular init <agent>` once to pick up the new layout.

## 18_release_workflow

Spektacular now has a complete automated release pipeline powered by Dagger and GitHub Actions. Every push to any branch builds cross-platform binaries (darwin/linux on amd64/arm64) with automatic macOS code signing and notarization. Merging to `main` with a `release/patch|minor|major` PR label automatically publishes a new release to GitHub Releases, updates the Homebrew formula in `jumppad-labs/homebrew-repo`, and pushes packages to GemFury. Users can now install spektacular via `brew install jumppad-labs/repo/spektacular` or download signed binaries directly from GitHub Releases, eliminating the need to clone and build from source.
