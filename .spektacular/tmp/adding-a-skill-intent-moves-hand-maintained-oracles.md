# Adding an intent to a skill is a coordinated edit, not an insertion

A workflow skill's behaviour is prose, so its regression tests are phrase assertions on the
rendered file. `internal/agent/instruction_surface_test.go` holds several **hand-maintained
oracles** that describe the skill rather than being derived from it, and adding, removing or
renaming an intent must move them in the same change. Inserting the new section and stopping is
the trap, and it fails in two different ways depending on which oracle you missed.

**The skill's preamble counts its own branches, and the count is asserted as a literal.** For
`spek-knowledge`, `TestRenderedSpekKnowledgeAdvertisesAuditIntent` pins
`"picks one of four branches (lookup / contribute / update / audit)"` and
`"One skill handles all four intents"`, alongside a ban list of the superseded phrasings
(`"one of three branches"`, `"all three intents"`) so the old wording cannot survive beside the
new. A fifth intent therefore means editing both literals, adding the previous count to the ban
list, and adding a natural-language trigger under `# When to invoke`. This is not only a test
concern: **a branch the preamble does not advertise is never reached**, so the section would exist
in the file and never be chosen.

**A skill may only name CLI subcommands that are actually registered.** `knowledgeSubcommands` is
a closed `map[string]bool` mirroring the `AddCommand` call in `cmd/knowledge.go`, hand-maintained
because `cmd` imports `internal/agent` and reading it back would be an import cycle. Any
`<command> knowledge <verb>` appearing in a scanned section is checked against it, so a new intent
naming a legitimately new verb fails until the map gains it. The failure reads as "the intent
invokes a command `cmd/knowledge.go` does not register", which is confusing when you have just
registered it.

Two more move with an intent: `expectedCRUDInvocations` in
`TestRenderedSpekKnowledgeBodyContainsCRUDInvocations` lists the invocations the rendered skill
must contain, and the section-extractor helpers (`spekKnowledgeAuditSection` and any sibling)
slice from one `# Intent: <name>` heading to the next `\n# `, so inserting a section changes what
a neighbouring extractor returns. Assert that rather than assume it.

What to do instead: before editing a skill template, grep
`internal/agent/instruction_surface_test.go` and `templates/*_test.go` for the skill's name and
for its intent headings, and treat every literal you find as part of the change. The rendered copy
under `.claude/skills/` is regenerated by `migrate` and belongs in the same commit as the template
edit, since every assertion renders through the production install path rather than reading the
committed file.

`architecture/testing-architecture.md` records the same coupling problem for the harbor suites.
These oracles are the equivalent for prose-driven skill behaviour, and unlike harbor they do run
in CI, so the failure is immediate rather than deferred.
